# 测试驱动开发

## 使用示例
- 重构这个方法
- 根据方案设计接口
- 根据方案进行编码
- 对这个方法写单元测试
- 理解这个方案的领域模型

## 核心理念
**原则**：通过公共接口验证行为。代码可重构；测试不应失效。
**好测试**：通过公共 API，不 mock、不测私有方法、不直接查 DB。


## 禁止模式

| 禁止行为 | 正确做法 |
|---|---|
| **水平切片**：先写全部测试再写代码 | 垂直切片：一个测试一段实现重复 |
| **`@SpringBootTest` 测纯逻辑** | 纯逻辑用 JUnit + Mockito |
| **Mock 内部协作对象** | 只 Mock 系统边界 |
| **反射测私有方法** | 通过公共接口验证行为 |

## 工作流程

### 1. 规划

编写任何代码前：
- 在用户没有明确指明技术方案时，根据用户需求提出方案
- 领域上下文可以阅读 '/docs/architecture/service-map.md'，如果不存在可以先执行 `to-DDD.md`
- 与用户确认需要修改的接口
- 与用户确认需要测试的行为（划分优先级）
- 获得用户对方案的确认

主动询问："公共接口应该是什么样？哪些行为是最重要的测试点？"

**优先核心路径与复杂逻辑**。与用户确认最关键行为；无法测试所有场景。
**用户否决方案** → 记录分歧，回到讨论。
**无法确定优先级** → 从核心 happy path 开始。🔴

🔴 **CHECKPOINT**: 方案获用户批准方可进入编码。

### 2. 红-绿循环

为当前行为编写一个测试并实现。第一轮打通路径，后续增量推进。

```
红色：编写测试 → 编译失败或测试失败
绿色：编写使测试通过的最简代码 → 编译通过 + 测试通过
```

规则：
- 一次只写一个测试
- 只写满足当前测试的最少代码
- 不提前预判未来测试
- 测试始终聚焦可观测行为

**测试框架缺失** → 提示安装/配置，或退出手动验证。
**测试直接通过(未红先绿)** → 检查测试是否验证真实行为而非实现。
**编译失败** → 修复后重新从红色阶段开始。
**测试始终无法通过** → 检查设计假设，与用户确认边界。
**Bug 修复** → 先写复现测试 → 修复 → 回归验证。🔴

### 3. 重构

所有测试通过后，检查可重构点：
- 代码重复：抽取独立方法/类（见 design-an-interface.md）
- 方法过长：拆分为私有辅助方法
- 模块职责单薄/分散：合并或扩充
- 逐一检查 SOLID 是否被破坏
- 每一步重构后都运行测试

🔴 **CHECKPOINT**: 测试全绿方可重构；红色阶段不得重构。
**重构后测试失败** → 撤销重构，确认行为未变。
**跨模块影响** → 运行全量测试。

重构规则参见 [refactor.md](refactor.md)
