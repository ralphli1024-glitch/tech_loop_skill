# tech_loop_design_to_plan

规格→可执行计划：文件拆分→任务分解→契约提取→自检→交接。

## 设计原则

这份计划不是给人读的，是给智能体执行的。写计划的每一段都要问一个问题：

> **执行智能体看到这段信息，需要额外读几个文件才能理解我在说什么？**

目标是把智能体的"自己发现"降到零。智能体应该只做两件事：粘贴代码、跑命令。它不应该需要推导类型签名、猜测文件位置、或搜索插入锚点。

---

## 触发条件（何时使用本技能）

不是所有改动都需要 to-plan。执行前先评估复杂度。

### 评估矩阵

| 条件 | 加分 | 直接 coder | 走 to-plan |
|------|------|-----------|-----------|
| **涉及文件数** | ≤ 3 个文件 | ✅ | — |
| | ≥ 4 个文件 | — | ✅ 建议 |
| **设计文档粒度** | 包含完整接口签名/伪代码/实体定义 | ✅ 文档已接近计划 | — |
| | 只有概念性文字描述（"用MQ加速"） | — | ✅ 需要分解 |
| **跨模块数** | 单模块内改动 | ✅ | — |
| | 跨 2+ 模块 | — | ✅ 契约依赖需要显式管理 |
| **风险等级** | 纯新增、不影响现有数据/流程 | ✅ | — |
| | 涉及资金/合规/数据迁移/存量数据兼容 | — | ✅ 自检能提前发现遗漏 |
| **子Agent执行** | 单人单会话一次跑完 | ✅ | — |
| | 需要分发多人/多会话并行 | — | ✅ 依赖表是分发依据 |

### 决策规则

```
if (文件数 >= 4) or (跨模块数 >= 2) or (风险等级 == 高风险) or (子Agent分发):
    → 走 to-plan（本技能继续）
elif (设计文档粒度 == 概念级) and (文件数 >= 3):
    → 建议走 to-plan（分解成本 > 编码时的发现成本）
else:
    → 跳过 to-plan，直接使用 tech_loop_coder
    → 执行前将设计文档内容作为上下文加载即可
```

### 跳过时的做法

当条件判断为"直接 coder"时：

1. 不执行本技能
2. 直接将设计文档（方案文档）作为编码上下文
3. 调用 `tech_loop_coder` 开始编码
4. 编码过程中遇到模糊点，回读设计文档确认，不需要写 plan

## 工作流

| # | 步骤 | 约束 |
|---|------|------|
| 0 | **复杂度评估** — 按触发条件矩阵评估是否执行to-plan | 不满足条件 → 跳过本技能，直接调用 tech_loop_coder；满足 → 继续 Step1 |
| 1 | **范围检查** — 多子系统则拆为独立计划 | 每计划一个子系统 |
| 2 | **文件结构** — 定文件创建/修改及职责 | 一文件一职责，按职责不分层 |
| 3 | **任务分解** — 每步2-5分，一个操作一步 | — |
| 3.5 | **提取共享契约** — 跨任务共享的类型/枚举/DTO/映射器，写入计划中"共享类型与契约"段 | 每个跨任务引用的符号都必须在此定义，**禁止**在任务代码中使用未在契约段声明的外部类型 |
| 4 | **写计划头** → 目标/架构/技术栈/范围边界 | — |
| 4.5 | **写执行前导信息** → 上下文预读清单、任务依赖关系表 | 按执行智能体的阅读顺序组织 |
| 5 | **写任务** — 含路径+测试+实现+提交（完整代码） | 无TODO/占位符 |
| 6 | **自检** — (a)规格全覆盖 (b)无占位符 (c)类型一致 (d)契约完备 (e)锚点准确 | 🔴 **内联修复后继续** |
| 7 | **保存+审** — 保存，可选子Agent复审 | 🔴 **确认后再交接** |
| 8 | **选执行方式** — 子Agent/内联 | 🔴 **确认后执行** |

## 失败模式

| 问题 | 处理 |
|------|------|
| 自检发现空白（Step6） | 回 Step5 补任务再自检 |
| 任务过大（>10步） | 拆为子任务或独立 |
| 规格有歧义/矛盾 | 标"此假设待确认" → 写入计划头"关键假设"段，继续 |
| 任务类型/命名不一致 | 回 Step5 统一后提交 |
| 子Agent复审发现问题 | 回 Step5 修复后重新自检 |
| 执行中计划不适配 | 标记变更点，继续执行 |
| **契约段缺失跨任务类型** | 回 Step3.5 补充后再自检 |
| **复杂度评估判断错误**（本应走to-plan却跳过） | 如果直走 coder 后发现改动量超出预期，停下并回头执行 to-plan |

## 文件结构

- **一文件一职责**：定义输入/输出/依赖
- **按业务拆**（用户/订单/支付），**不按技术层**（contr/serv/dao）
- **循现有**：现有库大文件则沿用，仅改到的边界不清才拆

### 任务结构注解

每任务的 5 步是固定的 TDD 循环，不得删减步骤或合并步骤。

**定位锚点规则：**
- 有明确行号：`FileName.java:85` — 在 `handleSignResult()` 调用之后追加
- 行号不确定：`FileName.java` — 在 `handleSignResult(body, type)` 调用之后、`return true` 之前追加
- 新文件（创建）：不需要锚点

**关键决策规则：**
- 代码中的设计约束（如"必须在 updateStep 前设置"、"异常不能抛出"）
- 用 `// REASON: 说明` 写在代码旁
- 不写显而易见的决策（如"用 for 循环而不是 while"）

## 自检

1. **规格覆盖**：各要求有对应任务？有缺口则补
2. **占位符**：扫 TODO/待定/稍后/类似任务X
3. **类型一致**：后任务类型/签名与前者一致？否则 bug
4. **契约完备**：计划中"共享类型与契约"段是否覆盖了所有跨任务引用的类型/枚举/映射器？漏了则回 Step3.5
5. **锚点可定位**：每个 `修改:` 文件是否都有定位锚点（方法名或行号）？缺了则补。例外：新增文件不需要锚点。
6. **验证清单完整**：`执行验证` 段是否覆盖了项目特定的验证项

## 执行交接

计划保存后：

> **子Agent（推荐）** → 每任务新子Agent+两阶段审
> **内联** → 用 executing-plans 批量+检查点

执行后更新进度到计划文档，标记已完成的步骤。

引用技能可用性：tech_loop_exec_plan 应已注册。

## 反例

| # | ❌ 禁忌 | 理由 |
|---|--------|------|
| 1 | 步骤留 TODO/待定 | 子Agent遇卡会瞎猜 |
| 2 | 跳过自检直接交接 | 不一致/遗漏是最大风险 |
| 3 | 复制模板不改内容 | 每任务需具体代码路径 |
| 4 | 任务覆盖多组件 | 粒度大，无法独立测试提交 |
| 5 | 代码只写"参考任务N" | 子Agent可能乱序读任务 |
| 6 | 步骤缺完整代码和命令 | 无上下文会猜错 |
| 7 | 不自检强行提交 | 规格缺口/命名bug直接进执行 |
| **8** | **任务代码引用未在契约段声明的外部类型** | 执行智能体需要回读设计文档验证签名，违反"零发现"原则 |
| **9** | **修改文件缺定位锚点** | 执行智能体需要手动搜索插入位置，产生额外的 cat/grep 调用 |
| **10** | **未写范围边界** | 执行智能体可能延伸实现未要求的功能，浪费 token |
| **11** | **应走 to-plan 却跳过直接 coder** | 大改动没有经过分解和自检，容易遗漏文件或类型不一致。如果已跳过但在编码过程中发现改动量超出预期，暂停并回头执行 Step0→to-plan |

## 写计划时的心智模型

写计划时，想像你面前有一个智能体正在执行它：

1. **它能看到什么？** 它能看到计划文件内容，以及项目的文件系统。它**不知道**设计文档、需求会议、技术讨论的任何背景。
2. **它需要做什么？** 打开文件 → 定位插入点 → 粘贴代码 → 跑测试 → 提交。每一步都应该可以从计划内容直接推出来。
3. **它会在哪里卡住？** 引用了一个它没见过的类名/方法名；不知道一个调用应该加在某个方法的哪一行；不确定一个值应该是什么类型。**这些地方就是你需要补充信息的位置。**
